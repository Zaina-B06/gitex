# Rebound — project context for coding agents

> Put this file in the repo root (also copy it to `CLAUDE.md` if your agent reads that name).
> Read it fully before any task. Task files in `docs/tasks/` say what to build next.

## 1. What we're building

**Rebound** is an adaptive behaviour-change engine for the Future Health Digital Innovation
Challenge 2026 (Abu Dhabi), problem "Sustaining Healthy Behaviors".

It gives each user one small health action per day (movement + sleep for the prototype),
tracks a **habit-strength score that decays instead of resetting**, detects when a user is
**drifting** before they fully lapse, asks a short blame-free check-in to find the **barrier**,
and adapts the next action (size, type, timing, channel). A **contextual bandit** learns per
user which adaptations work, always inside **hard safety rules**. Every action carries a
**"why this?"** explanation naming its behaviour-change technique (BCT Taxonomy v1).

We prove it works with a **synthetic population simulator** (≈300 personas × 90 days) that
compares: (A) a static streak app baseline, (B) Rebound rules-only, (C) full Rebound.

**Deadline: working prototype + technical docs + assumptions/dependencies/limitations due 20 Nov 2026.**

## 2. Non-negotiables

1. **Never reset progress to zero.** No streak counters anywhere in the product.
2. **Safety rules run before any personalisation.** The bandit only chooses among actions the safety layer allows.
3. **No real personal data.** All data is synthetic (generated by our code). Every external dataset/API must be listed in `docs/DATA_SOURCES.md`.
4. **Data minimisation.** Collect only fields that change the plan or safety. Sensitive fields are optional and show a "why we ask" line.
5. **No weight/calorie targets, no diagnosis, no medication advice.** Body measurements are used internally for intensity calibration only and never shown as goals.
6. **Employers see aggregates only** (minimum group size k ≥ 10). No endpoint returns individual data to an org.
7. **Engine is a pure Python package** with no web/DB imports, so the simulator and API run the *same* code.
8. **Deterministic and reproducible:** every random process takes a seed.

## 4. Onboarding profile (the data we collect)

Group fields so the UI can show them in steps. **Required** = needed to build a safe first plan. Everything else is optional with a skip button.

### 4.1 Basics (required)
| Field | Type | Used for |
|---|---|---|
| `language` | `ar` \| `en` (\| `hi`/`ur` stretch) | All UI and messages |
| `age_years` | int, 18–100 | Starting tier, safety (≥65 → balance-friendly start) |
| `sex` | `female` \| `male` \| `prefer_not_to_say` | Pregnancy question visibility; sleep/activity norms in sim |
| `goals` | list of `movement` \| `sleep` | Which behaviours get actions |
| `schedule_type` | `office` \| `shift` \| `outdoor_manual` \| `home_caregiver` \| `student` \| `other` | Time windows, context |
| `usual_wake_time`, `usual_sleep_time` | HH:MM | Action windows, sleep baseline |
| `work_hours` | optional ranges; for shift workers a rotating pattern | Quiet hours, windows |

### 4.2 Body (optional; "used only to set a safe starting intensity, never shown as a target")
`height_cm`, `weight_kg` → internal BMI band only, to cap starting intensity. Never displayed, never a goal.

### 4.3 Health screening (required, yes/no; modelled on PAR-Q+ — paraphrase, don't copy verbatim)
1. Heart condition or high blood pressure
2. Chest pain at rest, during daily activities, or during exercise
3. Dizziness causing loss of balance, or fainting, in the last 12 months
4. Another long-term condition (e.g. diabetes, asthma)
5. Taking prescribed medication for a long-term condition
6. Bone, joint or muscle problem that more activity could make worse
7. A doctor said you should only exercise under supervision

Plus: `pregnant` (shown only if sex = female; yes/no/prefer not to say), `mobility_limitation` (none / some / uses mobility aid or wheelchair).

**Rules:** any "yes" on Q1–Q7 → `screening_flag = true` → movement tiers capped at 2, show "Please check with your doctor before increasing intensity", log it. Q2 or Q3 = yes → also show a "see a doctor" prompt and start with sleep/gentle actions only. Pregnant → pregnancy-safe action subset. Mobility limitation → seated/adapted action variants.

### 4.4 Activity and sleep baseline (required, quick)
`active_days_per_week` (0–7), `typical_daily_steps` (optional/unknown), `sleep_hours_typical`, `sleep_quality_self` (1–5).

### 4.5 Past history (optional but valuable; seeds the engine)
| Field | Type | Used for |
|---|---|---|
| `tried_before` | bool | Prior experience |
| `past_helpers` | multi-select: `small_steps`, `reminders`, `buddy`, `tracking`, `rewards`, `routine_anchor`, `other` | Prior over techniques (bandit warm start) |
| `past_stop_reasons` | multi-select from the **barrier taxonomy** (§6.2) | Prior over likely barriers; proactive plan tweaks |
| `smoking_status` | `never` \| `former` \| `current` \| `prefer_not_to_say` | Future smoking module; not used in movement/sleep logic |
| `motivation_reason` | optional free text, ≤ 200 chars. "Why we ask": *"We'll remind you of this on tough days."* | Shown back on `low_motivation` (§6.3); red-flag checked (§6.4) at onboarding |

### 4.6 Preferences (optional)
`setting`: `indoor` \| `outdoor` \| `either`; `social`: `alone` \| `with_others` \| `either`; `space_preference`: `home` \| `women_only_spaces` \| `any`; `fasting_ramadan`: bool; `notification_window`; `quiet_hours`; `channel`: `app` \| `whatsapp_style` \| `voice_note`; `accessibility`: `large_text`, `high_contrast`, `screen_reader`.

### 4.7 Data controls
Per-field consent stored with each profile (`consents: {field_group: bool}`); users can view, edit, export and delete. Sensitive groups (body, screening, history) are stored separately from behaviour events.

## 5. Core models (Pydantic)

- `UserProfile`: all of §4 + `user_id`, `created_at`, `consents`.
- `Action`: `id`, `behaviour` (`movement`/`sleep`), `tier` (1–4), `title` (`en`/`ar`), `bct_code`, `bct_name`, `rationale`, `limits`, `setting` (`indoor`/`outdoor`/`any`), `fasting_safe` bool, `low_energy_ok` bool, `seated_variant_id` optional, `pregnancy_safe` bool, `contraindications` list, `duration_min`.
- `Event`: `user_id`, `day`, `type` (`action_shown`/`completed`/`partial`/`skipped`/`no_response`/`checkin`/`pause`), `action_id?`, `payload`.
- `UserState`: `habit_strength` per behaviour, `engagement_state`, `current_tier` per behaviour, `context_flags`, `bandit_params`, `last_barrier?`.

## 6. Engine rules

### 6.1 State
- Habit strength per behaviour: `H_t = λ·H_{t-1} + (1−λ)·a_t`, λ = 0.9, `a_t` = 1.0 full, 0.5 smaller version, 0 skip/no response. **Paused days and declared illness days don't update H.**
- Engagement state over a rolling 7-day window (completions incl. partials):
  `active` ≥ 4/7 · `drifting` 2–3/7, or a drop of ≥ 50% vs. the user's own previous 7 days · `lapsed` 0–1/7, or ≥ 3 consecutive no-response days · `recovering` = was lapsed and now has ≥ 2 completions in the last 4 days.
- Context flags: `ramadan`, `heat`, `shift_pattern`, `travel`, `illness`, `paused`.

### 6.2 Barrier taxonomy (fixed enum)
`time`, `energy_fatigue`, `illness_pain`, `schedule_change`, `environment` (heat, no safe space), `low_motivation`, `social_family`, `forgot`, `other`.

### 6.3 Policy (in this order)
1. **Safety filter:** remove actions that break screening rules, pregnancy/mobility constraints or context (outdoor in heat mode between 11:00–16:00; strenuous while fasting; anything after an illness/pain flag until the user says they're OK).
2. **Rules layer:** barrier → adjustment
   - `time` → tier −1, add an implementation intention ("After X, I will Y")
   - `energy_fatigue` → tier −1, prioritise sleep actions
   - `schedule_change` → move the time window
   - `low_motivation` → re-show the user's own stated reason + optional buddy
   - `forgot` → change prompt time/channel
   - `illness_pain` → pause movement and show a care message
   - `environment` → swap to indoor/home variant
3. **Bandit (Thompson sampling):** among allowed actions, arms = (tier, bct_code, time_window, channel). Beta priors per arm, warm-started from `past_helpers`. Reward = completion within 24h (1, partial 0.5).
4. **Step-up:** after 3 successful days at a tier, go up one tier (never jump back to the pre-lapse tier directly). Max tier respects the safety cap.

### 6.4 Red flags (in any free text)
Chest pain, fainting, severe breathlessness, self-harm language, disordered-eating signals → stop coaching, show a supportive message + "seek care" guidance, write a `red_flag` event. Keyword + LLM check; keyword match alone is enough to trigger.


## 8. Working conventions

- Small commits, one feature each. Tests in `engine/tests` for every rule in §6.
- Type hints everywhere; Pydantic for all I/O.
- Config (λ, thresholds, tier caps) lives in one `config.py` / YAML. No magic numbers in logic.
- Write a short note in `docs/ASSUMPTIONS.md` whenever you choose a number or rule we haven't justified.
- **The developer runs commands themselves.** Don't run long scripts, servers or test suites and summarise the output. Give the exact commands to run (and what output to expect); the developer will run them in their own terminal and paste back anything that fails.
- Never commit `.env`. Only `.env.example` (empty keys) is in the repo.
- Commit messages carry no tool attribution: no `Co-Authored-By`, "Generated with Claude Code" or `Claude-Session` lines (the project's `.claude/settings.json` sets `"includeCoAuthoredBy": false`).
- Agents: make edits that contain escape sequences (`\n`, `\r`, `\"`) with an editor tool, not shell heredoc scripts. On Windows Git Bash a `\\n` in a heredoc reached Python as a real line break and broke a file.

## 9. Evaluation rules (simulator)

The simulation is our evidence, and "the simulation was rigged" is a named risk. These rules keep it honest.

1. **Pre-register before changing the model or the engine because of results.** Write the parameter, its value with reasoning, and the headline comparisons in `docs/ASSUMPTIONS.md`, and commit that alone before running anything.
2. **Calibrate on seed 101 only, arm A only** (100 personas), changing only the parameter named for calibration (`open_base`). Evaluation uses seeds 1–10, never used for tuning. A re-test of a pre-registered change uses fresh seeds (11–20).
3. **Never tune the engine to simulator results.** Knobs that look better in the sim (e.g. the step-up threshold) go into the sensitivity sweep or a pre-registered test on fresh seeds, and stay a pilot question until then.
4. **Pre-registered headline:** C vs A, C vs A0, C vs B on recovery within 14 days, persistence at week 12 and retention. Verdicts: **helps** = whole 95% interval above zero, **worse** = whole interval below zero, otherwise **not shown**. Report all of them, whatever the direction.
5. **Say plainly what a gain depends on** (e.g. the advantage over a streak app depends on the abstinence-violation assumption). A borderline pass among many tests is labelled weak evidence, not a finding.
6. **Keep earlier worlds documented**, e.g. the no-feedback run (run_002) under "Where Rebound doesn't help". Every run has a "Where Rebound doesn't help" section.
7. **Outputs produced against a stale calibration are invalid:** delete them and say so in `docs/ASSUMPTIONS.md`. `sim/out/` is never committed; the reviewed snapshot lives in `docs/results/`.
8. **The safety audit must be 0** for B and C (no unsafe action, no quiet-hour message); the run fails loudly otherwise.
